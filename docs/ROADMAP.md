# ROADMAP — Filmarks 型サービスを目指す

目標: **実際に人に使ってもらえる「美術館・展覧会版 Filmarks」**。

このドキュメントは、Filmarks の構造を分解して ArtMark との差分を整理し、
どの順に作るかを決めるためのものです。実装が進んだら随時更新します。

---

## 1. Filmarks を分解する

Filmarks は「レビューサイト」に見えて、実際には4つの層が噛み合った構造をしています。

### 層1: 作品データベース（サービスの土台）

約 15 万タイトル。1作品につき、あらすじ・製作年・製作国・上映時間・ジャンル・
監督・脚本・出演者・配給会社・シリーズ・ポスター画像を持ちます。
キャストや配給会社はそれ自体がページになっていて、そこから作品を辿れます。

**ここが最重要**。レビューを書く「対象」が網羅されていないと、ユーザーは
「自分が観た作品がない」で離脱します。Filmarks の参入障壁の本体はここです。

### 層2: 記録（一人でも成立する価値）

- **Clip（観たい）**: あとで観る作品をためる
- **鑑賞記録**: 観た事実 + 鑑賞日
- **レビュー**: 5段階 0.5 刻みのスコア、本文、ネタバレフラグ、ハッシュタグ
- スコアなしの「鑑賞記録だけ」も投稿できる（ハードルを下げる設計）

ログイン直後、フォロワーが0人でも使える。これが継続利用の入口になっています。

### 層3: 社会性（記録を資産に変える）

- ユーザーはハンドル（`@id`）とプロフィールを持つ
- フォロー / フォロワー
- レビューへの **いいね** と **コメント**
- 「人気のユーザー」導線、ユーザー検索
- 作品ページのレビュー一覧は「すべて / ネタバレなし / ネタバレ」で切替

レビューが「自分のメモ」から「他人に読まれるもの」に変わることで、
書く動機が跳ね上がる。ここが Filmarks の心臓部です。

### 層4: 発見（毎日来る理由をつくる）

- リアルタイム更新のランキング（「2026/08/30 13:00現在」と時刻が入る）
- 上映中 / 公開予定 / 今週公開
- 多面的な絞り込み: 配信サービス・映画賞・製作年・国・ジャンル・配給会社・#タグ
- 「似ている作品」レコメンド
- 映画館検索（地域から / 現在地から）
- FILMAGA（オウンドメディア）と物販ストア

## 2. ArtMark の現状

| 層 | 実装状況 |
| --- | --- |
| 層1 データベース | ❌ 美術館10件・展覧会15件のハードコード |
| 層2 記録 | 🔺 Clip（行きたい／行った）とレビュー投稿はあるが localStorage のみ |
| 層3 社会性 | ❌ 未着手。ユーザーの概念がなく、レビューは自分にしか見えない |
| 層4 発見 | 🔺 キーワード検索とジャンル絞り込みのみ |

**構造上の最大の問題**: バックエンドがないため、レビューが自分のブラウザから出られません。
層3・層4 は、サーバーとデータベースなしには一歩も進めません。

## 3. 映画と展覧会の決定的な違い

Filmarks をそのまま移植すると失敗します。対象の性質が違うためです。

| | 映画 | 展覧会 |
| --- | --- | --- |
| 存在期間 | 半永久（配信で今も観られる） | **数週間〜数ヶ月で消える** |
| 追体験 | 誰でもあとから観られる | **会期が終わったら二度と観られない** |
| 場所 | 全国の映画館で同じ作品 | **その美術館に行くしかない**（巡回展は例外） |
| 母数 | 年間 約1,200本の公開作品 | 年間 数千件（小規模含む）、DB化されていない |
| レビューの価値 | 「観るかどうか」の判断材料 | **「会期内に行くかどうか」の判断材料** |

ここから導かれる、ArtMark 固有の勝ち筋:

1. **会期のカウントダウン** — 「残り9日」「今週末で終了」は Filmarks にない緊急性。
   通知・リマインドの強力な理由になります。
2. **行った記録の希少性** — 「もう観られない展覧会を観た」記録は、映画より価値が高い。
   年間の鑑賞履歴を振り返るコンテンツ（年間ベスト展覧会）が刺さります。
3. **位置情報との相性** — 「今いる場所から行ける、今週で終わる展覧会」は
   映画にはない体験。地図・現在地検索の優先度が Filmarks より高いです。
4. **混雑情報** — 展覧会特有の最大の不満。「土曜午後は60分待ち」は
   レビュー本文より価値のある情報になり得ます。

### Phase 1: バックエンド導入（最重要・2〜4週間）

**ここを越えないと Filmarks 型にはなりません。**

推奨は **Supabase**。理由は、PostgreSQL・認証・ストレージ・行レベルセキュリティが
一体で提供され、フロントエンドから直接叩けるためバックエンドのコードをほぼ書かずに済むこと。
無料枠で個人開発の規模なら十分で、Vercel との相性も良好です。

- [x] `@supabase/supabase-js` と TanStack Query を導入
- [x] テーブル定義（`supabase/migrations/0001_init.sql`）
- [x] 認証（マジックリンク + パスワード）と `AuthContext`
- [x] `ReviewContext` / `ClipContext` の localStorage 実装を Supabase 呼び出しに差し替え
- [x] Row Level Security 設定
- [x] モックデータの seed SQL 生成（`scripts/generate-seed.mjs`）
- [x] Supabase プロジェクトを作成し、ローカルで接続・ログイン・レビュー投稿を確認
- [ ] Vercel に環境変数を設定して本番でも動かす
- [ ] 独自 SMTP（Resend など）の設定 — 無料枠の送信制限は 1時間あたり 2通
- [ ] Google ログインの追加（Supabase 側の設定のみで切り替え可能）

#### スキーマ案

```sql

              price, image_url, official_url
```

#### 会期終了リマインドをメールでも送るには

現在はアプリを開いたときに気づける形（アプリ内通知）です。メールやプッシュで
届けるには、次の3つが必要になります。

1. 独自 SMTP（Resend など）— Supabase 無料枠の送信制限では実運用に耐えません
2. Supabase Edge Function — 「残り3日のクリップ」を集めてメールを組み立てる
3. `pg_cron` で毎朝1回その関数を叩く

「観に行きたかったのに会期が終わっていた」は展覧会サービス最大の失望なので、
ここは実装する価値が高い部分です。ただし送信の失敗やスパム判定の運用が伴うため、
ユーザーが増えてから着手するのが現実的です。

#### 地図の技術選定について

Leaflet + OpenStreetMap の生タイルを使っています。API キーも課金も不要で、
個人開発の規模なら十分です。ただし OSM のタイルサーバーには利用ポリシーがあり、
アクセスが増えたら MapTiler や Carto など（無料枠あり）に切り替える必要があります。
切り替えは `MuseumMapImpl.tsx` の `TileLayer` の URL 1行で済みます。

Leaflet 本体は 156KB あるため、地図を表示する画面でのみ遅延読み込みしています。

### Phase 4: データ調達（最大の難所・継続課題）

**正直なところ、ここが一番きつく、そして最も価値があります。**
映画の TMDb にあたる、展覧会の網羅的なオープンデータは日本に存在しません。

現実的な手段を、組み合わせて使います。

| 手段 | 得られるもの | 難易度 |
| --- | --- | --- |
| Wikidata / Wikipedia API | 美術館の基本情報（名称・所在地・座標） | 低 |
| Google Places API | 美術館の住所・営業時間・座標・写真 | 低（有料枠あり） |
| 各館の公式サイトを定期巡回 | 展覧会の会期・タイトル・料金 | 中〜高 |
| ユーザー投稿で展覧会を登録 | 網羅性（小規模ギャラリーまで） | 中（荒らし対策が必要） |
| 美術館の公式 SNS / RSS | 新規展覧会の検知 | 中 |

**現実的な進め方**: まず美術館マスタを Wikidata + Google Places で機械的に埋め、
展覧会は「主要50館を巡回スクレイピング + ユーザー投稿で補完」の二本立てにする。
スクレイピングは各サイトの利用規約と robots.txt を必ず確認し、
アクセス間隔を空けること。可能なら公式に許諾を取るのが最善です。

## 5. 技術的に追加が必要になるもの

| 課題 | 現状 | 導入するもの |
| --- | --- | --- |
| データ取得と状態管理 | Context + localStorage | TanStack Query（キャッシュ・再取得） |
| フォーム | 手書きの useState | React Hook Form + Zod（バリデーション） |
| 画像 | picsum のダミー | Supabase Storage / Cloudinary |
| SEO | SPA なので検索エンジンに不利 | 将来的に Next.js への移行を検討 |
| テスト | なし | Vitest + Testing Library |
| CI | なし | GitHub Actions で lint / build を PR ごとに実行 |

**Next.js への移行について**: レビューサイトは検索流入が生命線なので、
本気で人に使ってもらうなら SSR/SSG はいずれ必要になります。
ただし Phase 1〜2 の間は現状の Vite + React で進め、
機能が固まってから移行を判断するのが安全です。今やると学習コストで止まります。

## 6. 次の一手

Phase 1 の Supabase 導入が全ての前提になります。具体的な最初の3ステップ:

1. Supabase でプロジェクトを作り、上記スキーマでテーブルを作成する
2. 認証（メールログイン）だけを先に通し、ログイン状態が保持されることを確認する
3. `ReviewContext` の localStorage 部分を Supabase に差し替える
   （Clip はそのあと。レビューのほうが検証したいことが多い）

ここまで動けば、「他人のレビューが見える」という Filmarks の核が手に入ります。
